## How I work

My process usually starts with a stakeholder problem, not with code.

**1. Understand the work**  
I talk with the people doing the work to understand the actual problem, constraints, ownership, and what "done" needs to look like.

**2. Design the workflow**  
Before building anything, I determine the structure: what needs to be tracked, how information should move, what should be automated, and what people still need to own.

**3. Build with AI**  
I use AI as a development partner to help translate requirements and business logic into working automation. This can include Python scripts, API interactions, formulas, and GitHub Actions workflows.

**4. Test before production**  
Automations are tested in a controlled environment first. For Python-based workflows, I use Google Colab and dry-run logic to review the exact proposed changes before anything touches a live system.

**5. Deploy and operate**  
Once validated, automations can be deployed through GitHub Actions on scheduled workflows so recurring operational work happens automatically.

**6. Document what we learn**  
API behavior, platform limitations, edge cases, and reusable patterns are documented so the system becomes easier to maintain and improve.

## My development approach

I don't position myself as a traditional software engineer. My strength is connecting **people, process, systems, and technology**.

AI helps me develop faster, but the work still requires defining the right problem, designing the business logic, understanding exceptions, testing against real workflows, validating results, and determining whether an automation actually improves the way a team works.

`Stakeholder need → Process discovery → Workflow design → AI-assisted development → Dry-run testing → Validation → Deployment → Documentation`
